01

What DisCache does

DisCache is a small distributed in-memory cache. It keeps frequently used key-value data across three data nodes and routes each key to one owner.

Your app→Coordinator→One of 3 data nodes

The coordinator routes requests; data nodes store values. The website's default playground is a browser simulation, not a live cluster.

02

Navigate and run a request

Playground runs requests. How it works explains routing, cache order and recovery. Performance shows benchmark data.

  1. Keep the sample key and value, or enter your own.
  2. Choose PUT, GET or DELETE; the hint beside the controls explains it.
  3. Press Run, or Step to reveal the request path.
What do the buttons do?

Run plays the request path. Step Forward reveals one stage at a time. Reset clears the browser simulation and its sample log; it never clears live backend data.

03

PUT, GET and DELETE

  • PUTStore or replace a value. Requires a key and a value. Expect “Value stored”.
  • GETLook up a key. A hit returns its value; a miss says “Key not found”.
  • DELETERemove a key. It reports “Key deleted” or “Key not found”.

A destination node identifies where the request was routed. “Cache / log” summarizes actual changes, and Recent requests shows prior results.

Technical response status

OK means the operation succeeded; NOT_FOUND is a cache miss or missing delete target; ERROR means the request failed. Detailed response fields are in the Playground's Technical details panel.

04

Coordinator and data nodes

The coordinator receives a request and forwards it to the chosen node. Each of the three independent data nodes owns its own cache and local write-ahead log (WAL: a record of changes).

There is no replication or automatic failover. A node's cached value is not copied to the other two nodes.

05

How routing chooses a node

Consistent hashing places each key and many virtual node positions on a circular hash ring. The coordinator selects the first virtual position clockwise from the key; its owner is the destination data node.

This gives the same key the same route while the ring stays unchanged. The interactive ring shows the real key hash, successor and node for the current sample.

More about the calculation

The current implementation uses MurmurHash3 x86-32 with seed 0 and 100 virtual positions per node (300 total). A lookup wraps to the ring start if the key hash is beyond the last position.

06

LRU cache and eviction

LRU means “least recently used.” Entries are ordered from most recently used (MRU) to least recently used. A successful GET promotes its entry to the front.

If a new PUT arrives when the cache is full, the least recently used entry is evicted. A cache miss does not promote anything.

07

WAL and recovery

For PUT and DELETE, a data node appends and flushes a WAL record before changing its in-memory cache, then responds. At startup it replays its local log to rebuild memory.

Flush is not an fsync guarantee against power loss. The How it works page can simulate losing browser cache memory and replaying the simulated log; it never crashes a real process.

08

Read benchmark results

Throughput is operations per second. P50 and P99 are latency percentiles in milliseconds: half and 99% of measured requests were at or below that time.

Check the source label: live runs require a connected C++ cluster, saved results are historical, imported JSON comes from your file, and generated samples are simulated—not measurements.

09

Common issues

  • Key required: enter a non-empty key.
  • Key not found: run PUT first, use the same key, and check whether it was deleted or evicted.
  • Live request unavailable: use the simulation, or start the coordinator and all three data nodes before switching to live mode.
  • Benchmark unavailable: load the saved measurement or generate clearly labeled sample data.
  • Unexpected route or result: reset the browser demo, check the selected operation, then inspect Technical details for the status and node.

SYSTEM DESIGN

Architecture and technical reference

How requests move from a client to one of three independent cache nodes.

One coordinator, three storage nodes

The coordinator owns the consistent-hash ring and forwards each request to one data node. The coordinator does not store cached values; each data node owns its own in-memory LRU cache and local write-ahead log.

The custom TCP protocol uses a 10-byte request header and a 16-byte response header. The request magic is 0xDC; GET, PUT and DELETE use opcodes 0x01, 0x02 and 0x03.

There is no replication or automatic failover. WAL writes use C++ stream flush, not an OS-level fsync guarantee.

DISTRIBUTED IN-MEMORY CACHE · C++20

DESIGN NOTE Why 100 Virtual Nodes per Physical Node?

With only 3 physical positions on the ring, random hash placement produces highly uneven arc lengths between nodes. By assigning 100 virtual labels (Node-1#VN-0 … Node-3#VN-99) to each physical Data Node—for 300 total positions stored in std::map<uint32_t, VirtualNode>—ownership arcs are interleaved finely across [0, 2^32 - 1].

Architectural Boundary & Caveats: Consistent hashing provides finer-grained statistical keyspace distribution, but does not guarantee identical key counts per node. In DisCache, consistent hashing is strictly a partitioning and routing mechanism—it does not automatically provide data replication or failover if a node stops.

CACHE MECHANICS LRU Cache Mechanics
  • Hash Map Lookup (average-case O(1)): std::unordered_map maps each key string to its Node* address inside the doubly linked list. Hash collisions can make lookup slower in the worst case.
  • Recency Tracking (O(1)): A custom doubly linked list maintains recency order. The HEAD pointer tracks the Most Recently Used (MRU) entry; the TAIL pointer tracks the Least Recently Used (LRU) entry.
  • GET & PUT Promotion (O(1) list work): Successful GET and PUT operations detach the target Node* via its prev and next pointers and attach it at HEAD. The cache protects a successful GET with an exclusive lock because recency changes.
  • DELETE Removal: DELETE unlinks the list node in O(1); std::unordered_map erase is average-case O(1).
  • Capacity Eviction: When size == capacity (100,000 by default, configurable above for experiments), the node unlinks TAIL in O(1) list work. Map removal is average-case O(1).
  • Strict Scope: No TTL, no EXPIRE timers, no transactions, and no alternative eviction policies are introduced.
CONCURRENCY Data Node Concurrency & Networking Pipeline
01 / INGRESS
TCP Sockets

Accepts persistent raw TCP binary connections from the Coordinator or load-test workers on port 8001–8003.

──►
02 / EVENT LOOP
select() I/O Multiplexing

Monitors multiple open socket file descriptors in a single event loop to detect readable sockets without blocking one thread per idle connection.

──►
03 / DISPATCH
Request Handling / Work Queue

Decouples the socket readiness notification stage from request execution by placing ready socket descriptors into a synchronization-protected bounded queue.

──►
04 / EXECUTION
Bounded Thread Pool

A fixed pool of pre-allocated worker threads dequeues socket tasks, parses the 10-byte binary frame, and executes operations without unbounded thread creation.

──►
05 / SYNCHRONIZATION
Cache Operation (std::shared_mutex)

Coordinates reader and writer thread access to shared cache state so concurrent workers never corrupt hash-map buckets or linked-list pointers.

READ REQUESTS (GET) & std::shared_mutex

A successful cache GET takes an exclusive lock (std::unique_lock) because promotion changes the doubly linked list. Read-only snapshots can use shared locks; operations do not execute unsynchronized in parallel.

MUTATION REQUESTS (PUT / DELETE)

Mutations append to the node's Write-Ahead Log and call C++ stream flush(), then acquire an exclusive lock (std::unique_lock<std::shared_mutex>) on the LRUCache. The implementation does not call OS-level fsync().

TECHNICAL REFERENCE

Systems Engineering Reference & Verification Guide

Summary of the 10 core engineering mechanisms demonstrated in DisCache.
01 · SYSTEM IDENTITY
What is DisCache?

A dependency-free distributed in-memory key-value caching system written from scratch in C++20 using raw TCP sockets and a custom binary framing protocol (0xDC).

02 · PROCESS TOPOLOGY
Why 1 Coordinator and 3 Data Nodes?

Separates stateless consistent-hash request routing (Coordinator :8000) from stateful in-memory storage and local WAL persistence across three isolated Data Node processes (:8001–:8003).

03 · HASH RING ROUTING
How does consistent hashing select a node?

The key is hashed via 32-bit MurmurHash3_x86_32, and the Coordinator executes std::map::lower_bound(hash) to find the next clockwise virtual node, wrapping to begin() past 2^32 - 1.

04 · VIRTUAL NODES
What do the 100 virtual nodes accomplish?

Mapping each physical node to 100 positions (300 total ring entries) interleaves arcs across the 32-bit ring for finer-grained keyspace partitioning than 3 raw points.

05 · O(1) LRU ENGINE
How does the LRU data structure work?

Combines average-case O(1) std::unordered_map<string, Node*> lookup with O(1) doubly linked-list operations. HEAD is MRU; TAIL is the next eviction candidate.

06 · NETWORK & CONCURRENCY
How are sockets and concurrency organized?

Each node uses select() I/O multiplexing to detect readable sockets, dispatches requests to a bounded worker thread pool, and guards cache state with std::shared_mutex.

07 · WRITE-AHEAD LOGGING
Why does a mutation enter WAL before success?

The guided crash is simulated in the browser. The node appends a record and calls C++ stream flush() before updating RAM. Replay can rebuild state when the log record is present, but there is no power-loss durability guarantee because the implementation does not call fsync() or fdatasync().

08 · CRASH RECOVERY
How is cache state reconstructed after restart?

At startup, each Data Node reads its local node_X.log sequentially from beginning to end, re-applying recorded PUT and DELETE operations to rebuild its LRUCache.

09 · BENCHMARKING
How are throughput, P50, and P99 measured?

load_tester.py spawns 50+ concurrent worker threads issuing timed binary TCP requests, dividing total completed ops by wall-clock time and sorting per-op RTTs for P50 and P99.

10 · EXECUTION BOUNDARY
Which elements are simulated vs. live execution?

In Demo Mode, the browser runs a deterministic JS engine with identical MurmurHash3 and LRU logic. When connected via bridge.js, commands and Python benchmarks execute against the live C++20 processes.
